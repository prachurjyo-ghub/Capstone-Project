# Phase 3: communication, notifications, jobs and catalogue cache

## Communication API

All routes use the standard response envelope and require a valid access token/session.
Supplier calls also send `x-business-id`; the server re-derives and validates active membership.

- `GET /api/v1/communications/conversations?page=1&pageSize=20&type=REQUEST`
- `POST /api/v1/communications/conversations` with exactly one of `requestId`,
  `quotationId`, or `orderId`. Customer/supplier scope is derived from authentication.
  Admins use `audience: CUSTOMER|SUPPLIER` and, for supplier threads, `businessId`.
- `GET /api/v1/communications/conversations/:id`
- `GET /api/v1/communications/conversations/:id/messages?pageSize=30&cursor=<message UUID>`
- `POST /api/v1/communications/conversations/:id/messages` with
  `{ "body": "...", "idempotencyKey": "client-generated-key" }`
- `POST /api/v1/communications/conversations/:id/read` with optional `messageId`.
- `POST /api/v1/communications/conversations/:id/messages/:messageId/attachments`
  sends a raw JPEG/PNG body and `x-file-name`. Maximum: three images per message,
  5 MiB per image, 8,000 pixels per dimension and 40 megapixels.
- `GET /api/v1/communications/conversations/:id/messages/:messageId/attachments/:attachmentId`
  performs the same conversation authorization before returning private bytes.

Message bodies are plain text, trimmed, 1–4,000 characters. Sends are rate-limited and
idempotent per conversation/sender/key. History sorts by `(sentAt, id)` and uses a stable
cursor. Read markers advance monotonically, including under concurrent requests.

Customer↔operations and supplier↔operations conversations have different deterministic
scope keys even when they reference the same request/order. There is no customer/supplier
direct channel, participant IDs are never accepted, and supplier identities are not exposed
to customers. Existing focused clarification records remain historical source records;
new general follow-up should use the linked conversation. Full messaging does not duplicate
those clarification rows.

Only actual raster JPEG/PNG data is accepted. Storage keys are generated by the server and
the existing private attachment adapter is reused. Production still requires an explicitly
injected durable attachment adapter.

## Notification API

- `GET /api/v1/communications/notifications?page=1&pageSize=25&unreadOnly=true`
- `POST /api/v1/communications/notifications/:id/read`
- `POST /api/v1/communications/notifications/read-all`

In-app notifications are per user. Event keys enforce exactly one projection for each
user/channel/domain event. Source writes for assignments, supplier clarification replies,
quotation submission, option publication, acceptance/order creation, fulfillment,
cancellation and returns enqueue a PostgreSQL outbox row in the same transaction using
database triggers. Message writes enqueue explicitly in the message transaction.

Notification wording is audience-specific and deliberately generic. It never embeds message
content, customer contact/address details, supplier costs, platform margin, password reset
tokens or invitation tokens. Email/SMS are injectable. Development may write safe messages
to `.local/notification-outbox`; production does not silently use that adapter. Provider
success means only that the provider accepted the delivery request—external delivery may be
duplicated under an at-least-once retry model.

## Worker and operational endpoints

The API and worker are separate processes:

```bash
npm run build
npm start
npm run worker
```

For development use `npm run dev` and `npm run worker:dev`. BullMQ schedules bounded jobs:

- durable outbox projection every 15 seconds;
- lifecycle reconciliation every minute;
- deadline/delivery reminders every 15 minutes.

Jobs use bounded attempts, exponential backoff, deterministic event/job scheduler keys and
bounded database batches. Each handler re-reads state. API-time deadline checks remain the
authority. Expiration never invalidates accepted commercial snapshots and no job cancels an
order or releases reservations automatically.

Admin/SUPER_ADMIN operational routes:

- `GET /api/v1/admin/jobs/outbox?status=FAILED`
- `POST /api/v1/admin/jobs/outbox/process`
- `POST /api/v1/admin/jobs/outbox/:id/retry`
- `POST /api/v1/admin/jobs/reconcile`
- `POST /api/v1/admin/jobs/reminders`

Failed events preserve only a safe error code. Raw provider responses and communication
content are not stored in job/audit metadata.

`GET /api/v1/health/readiness` reports database, Redis, worker availability, durable outbox
backlog and the catalogue fallback. If Redis is absent, requests and PostgreSQL outbox writes
continue; background execution reports unavailable until a worker can connect. The admin
process endpoint supports controlled local recovery.

## Lifecycle and time rules

All comparisons use UTC instants through the existing injectable clock. Exact deadline
boundaries are expired (`deadline <= now`). Reconciliation handles assignment deadlines,
quotation validity, published-option validity and expired CSV previews. Reminder event keys
include the relevant deadline, so retries do not create duplicate notifications and a
legitimate changed deadline can produce a new reminder. Urgent deadline breach is visibility
only; it does not promise an SLA or mutate financial/fulfillment state.

## Catalogue cache

Only shared supplier catalogue product lists/details are cached. Keys contain the environment
prefix and no user, customer, supplier inventory, authorization, stock or eligibility data.
TTL defaults to 120 seconds. Successful admin catalogue mutations bump a shared Redis
generation (and the local generation during an outage), invalidating cached entries across
API instances without a broad key deletion. PostgreSQL remains authoritative and a bounded
in-process cache keeps catalogue reads available during Redis outages. Inventory and
authorization are never served from this cache.

## Environment

- `REDIS_URL` — optional for the API, required to run the worker.
- `REDIS_KEY_PREFIX` — isolate development/test/production and test runs. Never `FLUSHDB` a
  shared instance.
- `CATALOGUE_CACHE_TTL_SECONDS` — 10–3,600.
- `JOB_BATCH_SIZE` — 1–500.
- `NOTIFICATION_EMAIL_ENABLED` / `NOTIFICATION_SMS_ENABLED` — disabled by default.
- `NOTIFICATION_OUTBOX_DIR` — ignored development-only sink.

No Redis service was added to Compose automatically: the local machine had no usable Redis
runtime and Phase 3 must not install system software without explicit approval. A compatible
loopback Redis can be supplied later through `REDIS_URL`.

## Frontends

The customer dashboard has a Messages section and header notification panel. The supplier
portal replaces its session-only message store and mock badge with live conversations,
attachments and notifications. Both poll at bounded intervals, pause polling in hidden tabs,
show empty/error/submission states and retain the existing authentication refresh behavior.
Operations remain API-only; use the admin routes above plus the conversation endpoint with an
explicit audience. WebSockets, full staff messaging and external providers remain later work.
